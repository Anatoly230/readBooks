## 3. Подготовка к выполнению: глобальный контекст выполнения

Перед выполнением кода движок создаёт **глобальный контекст выполнения**. Он состоит из:

- **LexicalEnvironment** (лексическое окружение) – хранит привязки переменных, объявленных через `let`, `const`, `class`, а также функции, объявленные через `function declaration` (но в глобальном коде они попадают и туда, и в VariableEnvironment).
    
- **VariableEnvironment** (переменное окружение) – хранит привязки, созданные через `var` и функции, объявленные через `function declaration` (именно они подвержены hoisting'у со значением `undefined` до инициализации).
    
- Внешнее окружение для глобального контекста — `null`.
    

На этапе создания контекста (ещё до выполнения кода) происходит **hoisting**:

- Все объявления `function foo` полностью поднимаются: создаётся функциональный объект, и идентификатор `foo` привязывается к нему в обоих окружениях.
    
- Все объявления `var a` также поднимаются, но их значение инициализируется как `undefined`.
    
- Объявления `let x` и `const` (внутри функций) не инициализируются: они находятся во **временной мёртвой зоне (TDZ)** до момента фактического выполнения строки с объявлением.
    

Итак, до выполнения глобального кода глобальное окружение содержит:

- `foo`: function object (уже полностью определён)
    
- `a`: `undefined` (var)
    
- `x`: неинициализировано (TDZ), но запись в окружении уже существует.
    

## 4. Выполнение глобального кода

Теперь движок начинает исполнять AST сверху вниз.

1. **`var a = 1;`**
    
    - Переменная `a` уже существует (была создана на этапе создания контекста). Присваиваем ей значение `1`.
        
    - В глобальном VariableEnvironment запись `a` теперь имеет значение `1`.
        
2. **`let x = 8;`**
    
    - Встречается объявление `let x`. Оно уже было создано в LexicalEnvironment, но находилось в TDZ. Теперь происходит инициализация: переменной `x` присваивается значение `8`. TDZ заканчивается.
        
3. **`function foo(x) { ... }`**
    
    - Объявление функции уже обработано на этапе создания контекста, поэтому эта строка не вызывает никаких дополнительных действий (функция уже существует). Однако в некоторых реализациях может происходить повторное связывание, но в целом функция уже готова.
        
4. **`foo(5);`**
    
    - Выражение вызова функции. Движок ищет `foo` в текущем окружении (находит функцию) и передаёт аргумент `5`. Это приводит к созданию **нового контекста выполнения функции**.
        

## 5. Вызов функции `foo(5)` — создание контекста выполнения функции

При вызове функции создаётся новый контекст выполнения, который помещается в стек вызовов. Этот контекст содержит:

- **LexicalEnvironment** (для `let`, `const` внутри функции).
    
- **VariableEnvironment** (для `var` внутри функции).
    
- Внешняя ссылка (`[[OuterEnv]]`) устанавливается на окружение, в котором функция была создана (в данном случае — глобальное окружение). Это обеспечивает замыкание.
    

Перед выполнением тела функции происходит инициализация параметров и объявлений:

1. **Параметр `x`**:
    
    - В VariableEnvironment (или LexicalEnvironment?) — параметры функций обычно связываются в отдельном declarative environment record, который становится основой для лексического окружения функции. В современной спецификации параметры обрабатываются в отдельном окружении, но для простоты считаем, что параметры попадают в окружение функции до выполнения тела.
        
    - Параметру `x` присваивается значение аргумента `5`.
        
2. **Объявления `var` и `let` внутри функции**:
    
    - Сначала создаются записи для всех идентификаторов, объявленных внутри функции, но с разным поведением.
        
    - **`var d`**: поднимается (hoisting) в VariableEnvironment функции со значением `undefined`.
        
    - **`let b`**: создаётся запись в LexicalEnvironment, но остаётся в TDZ до выполнения строки с объявлением.
        
    - Внутренние блоки (`if`, `while`) ещё не рассматриваются.
        

На этом этапе окружение функции выглядит так (до выполнения тела):

- LexicalEnvironment (включает параметры и let/const):
    
    - `x`: 5 (параметр)
        
    - `b`: <uninitialized> (TDZ)
        
- VariableEnvironment:
    
    - `d`: undefined
        
- Внешнее окружение: глобальное (содержит `a:1`, `x:8`, `foo`).
    

## 6. Выполнение тела функции

### 6.1. Первая строка тела: `var d = 30;`

- Присваиваем значение `30` переменной `d`. Переменная уже была в VariableEnvironment со значением `undefined`, теперь становится `30`.
    

### 6.2. Вторая строка: `let b = 2;`

- Инициализируем переменную `b`, которая находилась в TDZ. Значение `2` присваивается, TDZ завершена. Теперь LexicalEnvironment содержит `b:2`.
    

### 6.3. Вход в блок `if (x > 0)`

Перед выполнением блока `if` создаётся **новое лексическое окружение для блока** (если внутри есть объявления `let`, `const`, `class`). Это необходимо для `const c`.

- Новое окружение (block environment) связывается с текущим лексическим окружением функции как внешнее.
    
- В этом блоке объявляется `const c`. Создаётся запись в новом окружении, но она не инициализируется до выполнения объявления (TDZ для const тоже существует, но const требует инициализации при объявлении).
    

Затем выполняется условие: `x > 0` → `5 > 0` → `true`.

#### 6.3.1. Выполнение тела `if`:

- **`const c = 3;`**  
    Инициализация `c` значением `3`. TDZ заканчивается.
    
- **`console.log(a, b, c, x, d);`**  
    Движок вычисляет каждый аргумент, следуя цепочке областей видимости (цепочке окружений):
    
    - `a` — не найдено в текущем блоке → идём во внешнее (функция) → не найдено → идём в глобальное → находим `a = 1`.
        
    - `b` — в окружении функции `b = 2`.
        
    - `c` — в текущем блоке `c = 3`.
        
    - `x` — в окружении функции (параметр) `x = 5`.
        
    - `d` — в VariableEnvironment функции, но VariableEnvironment также просматривается через ту же цепочку? На самом деле в современной спецификации VariableEnvironment и LexicalEnvironment — это два разных компонента, но поиск идентификаторов идёт сначала по LexicalEnvironment, а потом по внешнему LexicalEnvironment. VariableEnvironment не участвует напрямую в цепочке для `let/const`. Однако переменные `var` тоже хранятся в LexicalEnvironment для целей поиска? Спецификация говорит, что VariableEnvironment тоже является разновидностью Lexical Environment, но используется для хранения var-объявлений. В большинстве реализаций для простоты можно считать, что `var`-переменные находятся в том же окружении, что и `let`, но с особенностями hoisting. В любом случае `d` будет найдено в окружении функции (оно доступно как переменная, объявленная через `var` в функции).
        
    - Вывод в консоль: `1, 2, 3, 5, 30`.
        

После выхода из блока `if` его лексическое окружение может быть уничтожено (сборщик мусора), если на него нет ссылок (замыканий). Здесь ссылок нет, поэтому `c` исчезает.

### 6.4. Цикл `while (a < 10)`

Перед первой итерацией проверяется условие: `a < 10` → `1 < 10` → `true`.

Каждая итерация цикла `while` (как и любой блок) создаёт **новое лексическое окружение для своего тела**, если в теле есть объявления `let`, `const`, `class`. Это нужно, чтобы переменные, объявленные внутри блока, не «вытекали» наружу и пересоздавались на каждой итерации (особенно важно для `let` в циклах с замыканиями). В нашем случае в теле `while` есть `let v`, поэтому каждая итерация будет иметь собственное окружение.

Порядок для **первой итерации**:

- Создаётся новое блоковое окружение, внешним для него является текущее лексическое окружение функции.
    
- В этом окружении создаётся запись для `let v` (пока в TDZ).
    
- Выполняется объявление: `let v = b + a;`
    
    - Вычисляется `b + a`: `b = 2`, `a = 1` → `v = 3`.
        
    - Инициализация `v`, TDZ заканчивается.
        
- Затем последовательно выполняются присваивания:
    
    - `a += v` → `a = a + v` → `1 + 3 = 4` (обновляется глобальная `a`).
        
    - `b += v` → `b = 2 + 3 = 5` (обновляется `b` в окружении функции).
        
    - `d += v` → `d = 30 + 3 = 33` (обновляется `d` в VariableEnvironment функции).
        
    - `x += v` → `x = 5 + 3 = 8` (обновляется параметр `x` в окружении функции).
        
- После завершения тела итерации её окружение уничтожается (но только если нет замыканий; здесь нет).
    

Теперь значения:

- глобальные: `a = 4`, `x = 8` (глобальный `x` не менялся, он отдельно, не путать с параметром)
    
- внутри функции: `b = 5`, `d = 33`, `x` (параметр) = `8`.
    

**Вторая итерация**:

- Проверка условия: `a < 10` → `4 < 10` → `true`.
    
- Создаётся новое блоковое окружение для тела цикла.
    
- Вычисляется `let v = b + a` → `5 + 4 = 9`.
    
- Присваивания:
    
    - `a += v` → `4 + 9 = 13` (глобальная `a` становится 13)
        
    - `b += v` → `5 + 9 = 14`
        
    - `d += v` → `33 + 9 = 42`
        
    - `x += v` → `8 + 9 = 17`
        
- Конец итерации, окружение удаляется.
    

**Третья итерация (условие проверяется после второй)**:

- `a < 10` → `13 < 10` → `false`. Цикл завершается.
    

Обратите внимание: несмотря на то, что условие проверяет глобальную `a`, внутри цикла мы её меняем, и на второй итерации она становится 13, поэтому третья итерация не выполняется.

### 6.5. Завершение функции

После выхода из цикла функция завершается. Возвращаемое значение отсутствует (функция возвращает `undefined` неявно). Контекст выполнения функции извлекается из стека, и все её внутренние окружения становятся доступными для сборки мусора (если нет внешних ссылок). Глобальные переменные `a` и `x` остаются изменёнными: `a = 13`, `x = 8`.

## 7. Завершение программы

Глобальный код завершён, программа ожидает событий (если это среда браузера или Node.js). В данном случае программа просто выполнилась и завершилась.

## 1. Создание объекта функции (во время компиляции/парсинга)

Когда парсер встречает объявление функции `function foo(x) { ... }`, он не выполняет её тело, а создаёт **объект функции** – специальный внутренний объект, который будет хранить код функции и метаданные, необходимые для её будущих вызовов.

### Внутренние слоты объекта функции

Спецификация определяет ряд внутренних слотов ([[ ]]), которые есть у каждой функции:

- **[[Environment]]** – это **самое важное** для замыканий. Сюда сохраняется ссылка на текущее лексическое окружение (на момент создания функции). В нашем случае это глобальное окружение. Именно оно станет внешним окружением при вызове функции.
    
- **[[FormalParameters]]** – список имён параметров. Для `foo` это `["x"]`.
    
- **[[ECMAScriptCode]]** – тело функции, представленное в виде AST (или уже скомпилированного байт-кода). Оно будет выполняться при вызове.
    
- **[[FunctionKind]]** – тип функции: `"normal"` (обычная), `"generator"`, `"async"`, `"asyncGenerator"`. У нас `"normal"`.
    
- **[[ThisMode]]** – определяет, как работает `this` внутри функции. Для обычных функций (не стрелочных) это `"global"` или `"lexical"`? На самом деле для обычных функций в нестрогом режиме `this` может быть глобальным объектом, в строгом – `undefined`. Но это зависит от режима кода. Здесь предположим нестрогий режим (поскольку не указан `"use strict"`), тогда `[[ThisMode]] = "global"` (в некоторых реализациях "non-strict").
    
- **[[Realm]]** – содержит глобальный объект, интроспективные функции (например, `eval`), и другую контекстную информацию. Обычно это текущий Realm.
    
- **[[ScriptOrModule]]** – ссылка на скрипт или модуль, в котором объявлена функция.
    
- **[[HomeObject]]** – используется для `super` (в методах классов). Здесь `undefined`.
    
- **[[ConstructorKind]]** – для классов: `"base"` или `"derived"`. У обычной функции это `"base"`, если она может быть вызвана с `new` (а может).
    
- **[[SourceText]]** – исходный код функции (используется для `toString`).
    

### Доступные свойства объекта функции (публичные)

Кроме внутренних слотов, объект функции имеет стандартные свойства:

- **`length`** – число параметров (до первого параметра со значением по умолчанию). У `foo` длина = 1.
    
- **`name`** – `"foo"`.
    
- **`prototype`** – объект с единственным свойством `constructor`, указывающим на функцию. Это свойство автоматически создаётся для всех обычных функций (не стрелочных) и используется, если функцию вызывать как конструктор.
    

Итак, после компиляции в памяти появляется объект, условно выглядящий так:

text

FunctionObject foo {
    [[Environment]]: globalEnv,
    [[FormalParameters]]: ["x"],
    [[ECMAScriptCode]]: AST_тела_функции,
    [[FunctionKind]]: "normal",
    [[ThisMode]]: "global",
    [[Realm]]: currentRealm,
    [[ConstructorKind]]: "base",
    [[HomeObject]]: undefined,
    [[ScriptOrModule]]: currentScript,
    [[SourceText]]: "function foo(x) { ... }",
    length: 1,
    name: "foo",
    prototype: { constructor: foo }
}

Этот объект привязывается к идентификатору `foo` в глобальном окружении (в глобальной области видимости). Причём, поскольку это `function declaration`, привязка происходит **до выполнения кода** (hoisting), поэтому вызов `foo(5)` работает даже если размещён до объявления.

## 2. Подготовка к вызову: создание контекста выполнения функции

Когда интерпретатор доходит до строки `foo(5)`, он инициирует вызов функции. Алгоритм вызова (Call) создаёт новый **контекст выполнения функции (Function Execution Context)**. Этот контекст будет помещён в стек выполнения (ExecutionContextStack).

### Структура контекста выполнения

Согласно спецификации, каждый контекст выполнения содержит следующие обязательные компоненты (поля):

- **LexicalEnvironment** – ссылка на **лексическое окружение**, которое используется для разрешения имён идентификаторов, объявленных через `let`, `const`, и захваченных из замыканий.
    
- **VariableEnvironment** – ссылка на **переменное окружение**, которое используется для хранения переменных, объявленных через `var`. В глобальном контексте они могут отличаться, но в функциональном контексте обычно LexicalEnvironment и VariableEnvironment ссылаются на одно и то же окружение? Нет, спецификация требует, чтобы они были отдельными Environment Records, но они могут быть связаны с одним и тем же объектом. Однако для соблюдения семантики var (hoisting) они разделены, хотя в большинстве реализаций они указывают на один и тот же Declarative Environment Record, но с разными наборами привязок? Давайте разбираться.
    
    На самом деле, при создании контекста функции:
    
    - Сначала создаётся новый **Declarative Environment Record** (назовём его `funcEnv`).
        
    - Затем **LexicalEnvironment** и **VariableEnvironment** инициализируются ссылками на этот `funcEnv` (т.е. оба указывают на один и тот же рекорд). Но потом, в процессе выполнения, для обработки блоков создаются новые LexicalEnvironment (для `if`, `while`), а VariableEnvironment остаётся неизменным. Таким образом, var-переменные оказываются на уровне всей функции, а let/const – в блочных окружениях.
        
    
    Поэтому можно считать, что на момент входа в функцию оба окружения указывают на один объект. Позже, при входе в блок, LexicalEnvironment заменяется на новое (с внешней ссылкой на текущее), а VariableEnvironment остаётся прежним.
    
- **Function** – ссылка на вызываемый объект функции (тот самый `foo`), чтобы можно было получить доступ к [[Environment]] и коду.
    
- **Realm** – тот же Realm, что и у функции.
    
- **ScriptOrModule** – ссылка на текущий скрипт/модуль (если есть).
    

Дополнительные поля могут присутствовать в зависимости от типа функции (генераторы, асинхронные), но для обычной функции они необязательны.

Итак, перед выполнением тела создаётся новый контекст:

text

FunctionExecutionContext = {
    LexicalEnvironment: funcEnv,
    VariableEnvironment: funcEnv,   // пока одно и то же
    Function: fooObject,
    Realm: currentRealm,
    ScriptOrModule: currentScript
}

### Создание окружения (Environment Record) функции

`funcEnv` – это новый **Declarative Environment Record**. Он создаётся специально для этого вызова. В него будут помещены:

- Привязки для параметров (в данном случае `x`). Значение параметра берётся из аргументов вызова (`5`).
    
- Привязки для всех объявлений внутри функции:
    
    - `var d` – создаётся в этом окружении, но с особым флагом? Вообще, var-объявления попадают в VariableEnvironment, но поскольку сейчас оба окружения ссылаются на один рекорд, то `d` будет просто создана. Однако для соблюдения hoisting она инициализируется значением `undefined`.
        
    - `let b` – также создаётся в этом же окружении, но остаётся **неинициализированной** (TDZ). Это значит, что до выполнения строки `let b = 2;` обращение к `b` вызовет ReferenceError.
        
    - Обратите внимание: `const c` и `let v` объявлены внутри блоков, поэтому они не будут созданы в окружении функции – они появятся позже, при входе в соответствующие блоки, в новых блочных окружениях.
        
- Также может быть создана привязка для `arguments` (если функция не в строгом режиме и не стрелочная). Для простоты предположим, что arguments тоже присутствует, но в данном примере он не используется.
    

Итак, после инициализации параметров и var-объявлений, но до выполнения тела, `funcEnv` содержит:

- `x`: 5 (инициализирована значением аргумента)
    
- `d`: undefined (var)
    
- `b`: <uninitialized> (TDZ)
    
- (возможно `arguments`: объект arguments)
    

Внешним окружением для `funcEnv` является `[[Environment]]` из объекта функции, т.е. глобальное окружение (globalEnv). Это обеспечивает доступ к глобальным переменным `a` и `x` (глобальному `x`, не путать с параметром).

### Процесс создания контекста по шагам (согласно спецификации)

1. **Let _calleeRealm_ be ? GetFunctionRealm(_F_).** (получаем Realm функции).
    
2. **Perform ? OrdinaryCallBindThis(_F_, _calleeRealm_, _thisArgument_).** (связывание this, для обычных функций).
    
3. **Let _result_ be OrdinaryCallEvaluateBody(_F_, _argumentsList_).** – здесь начинается основная работа:
    
    - Создаётся новый Environment Record (функциональное окружение) с внешним окружением = [[Environment]] функции.
        
    - Инициализируются привязки параметров (CreateListOfParameters).
        
    - Инициализируются var-объявления (обходом AST и созданием привязок со значением undefined).
        
    - Создаются привязки для let/const, но они остаются неинициализированными.
        
    - Затем выполняется тело функции (последовательность Statements).
        

## 3. Выполнение тела функции

Когда тело начинает выполняться, мы имеем текущий контекст с `LexicalEnvironment = funcEnv` и `VariableEnvironment = funcEnv`.

### 3.1. `var d = 30;`

- Находится привязка `d` в VariableEnvironment (или в текущем окружении, если они совпадают) и присваивается значение 30.
    

### 3.2. `let b = 2;`

- Привязка `b` уже существует в LexicalEnvironment (funcEnv) и находится в TDZ. При выполнении этой строки она инициализируется значением 2, TDZ заканчивается.
    

### 3.3. Вход в блок `if (x > 0)`

Для блока создаётся **новое лексическое окружение** (blockEnv):

- Его внешним окружением становится текущее LexicalEnvironment (funcEnv).
    
- Контекст выполнения временно меняет своё поле **LexicalEnvironment** на это новое окружение (VariableEnvironment остаётся funcEnv).
    
- В этом блоке встречается `const c = 3;`. Создаётся привязка `c` в blockEnv и инициализируется значением 3.
    

Теперь разрешение имён внутри блока:

- `a` – не найдено в blockEnv → ищем во внешнем (funcEnv) → не найдено → ищем в globalEnv → находим a = 1.
    
- `b` – не найдено в blockEnv → ищем в funcEnv → находим b = 2.
    
- `c` – найдено в blockEnv.
    
- `x` – найдено в funcEnv (параметр).
    
- `d` – не найдено в blockEnv → ищем в funcEnv → находим d = 30.
    

После выхода из блока LexicalEnvironment возвращается к предыдущему значению (funcEnv). Блоковое окружение может быть уничтожено (если нет замыканий).

### 3.4. Вход в цикл `while (a < 10)`

Перед каждой итерацией создаётся **новое лексическое окружение для тела цикла**, потому что внутри есть объявление `let v`. Это важно для изоляции переменных между итерациями.

- Для первой итерации: создаётся loopEnv, внешним становится funcEnv.
    
- Контекст временно устанавливает LexicalEnvironment = loopEnv.
    
- Выполняется `let v = b + a` – создаётся привязка `v` в loopEnv, инициализируется вычисленным значением.
    
- Выполняются присваивания: `a += v` и т.д. Поиск `a` идёт по цепочке: loopEnv → funcEnv → globalEnv (находит глобальную `a`). `b` и `d` ищутся в funcEnv, `x` (параметр) тоже в funcEnv.
    
- После завершения итерации LexicalEnvironment возвращается к funcEnv, loopEnv уничтожается.
    
- Следующая итерация создаёт новое окружение.
    

## 4. Завершение функции

Когда выполнение тела завершается, контекст функции извлекается из стека, и управление возвращается в вызывающий контекст (глобальный). Окружения, созданные для функции и её блоков, становятся недоступными (если нет замыканий) и подлежат сборке мусора.

## Резюме: что необходимо для существования FunctionExecutionContext

Контекст выполнения функции **не может существовать** без следующих компонентов:

1. **LexicalEnvironment** – хотя бы пустое, но обязательно ссылка на Environment Record, которая определяет, где искать переменные.
    
2. **VariableEnvironment** – также ссылка на Environment Record для var-объявлений.
    
3. **Ссылка на объект функции** (поле Function) – чтобы знать [[Environment]] и код.
    
4. **Realm** – для доступа к глобальным объектам и интринсикам.
    
5. **Связь с внешним окружением** – она обеспечивается через цепочку Environment Records, начиная с текущего LexicalEnvironment.
    

Без любого из этих элементов интерпретация кода была бы невозможна: неясно, как разрешать имена, какой код выполнять, как работать с `this` и т.д.

Надеюсь, этот детальный разбор помог вам увидеть внутреннее устройство функции и контекста выполнения в JavaScript!
